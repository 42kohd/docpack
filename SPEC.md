# docpack specification

Version 1.0 of the docpack dialect and package format. This document is
normative: the checker, the schemas in `schemas/1.0/` and the kit all conform to it.
The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119.

The specification has two halves:

1. **The dialect** (part A): what documentation authors write — Markdown files,
   YAML data files and a `product.yaml`.
2. **The package** (part B): what `docpack check` emits — a zip of JSON files
   that validates against `schemas/1.0/` and that any consumer can import.

---

# Part A — The dialect

## A1. Project layout

A docpack project is a directory with this shape:

```text
product.yaml            product facts and navigation (required)
docs/<slug>.md          one file per document, flat (no subdirectories)
data/flags.yaml         command-line flags
data/platforms.yaml     supported platforms
data/datasets.yaml      output datasets
data/fields/<id>.yaml   fields of one dataset; <id> is a dataset id
data/dashboards/<t>.yaml dashboards for one forwarder target <t>
data/releases.yaml      release history
assets/                 images and icons referenced by documents and data
dist/                   output, written by the checker
```

All data files are optional except `product.yaml`. A data file that is absent
is treated as an empty list. Files are UTF-8; line endings MAY be LF or CRLF.

## A2. Documents

A document is one `.md` file in `docs/`. It consists of YAML frontmatter
between two `---` lines, followed by a body made **only** of the constructs in
section A5. Anything else is an error.

### A2.1 Frontmatter

| Key | Applies to | Required | Value |
|---|---|---|---|
| `type` | all | yes | one of `landing`, `concept`, `howto`, `integration`, `format`, `reference`, `dashboard`, `release` |
| `slug` | all | yes | lowercase words joined by `-`; MUST equal the filename without `.md` |
| `title` | all | yes | string |
| `summary` | all | yes | string, one sentence; more than 160 characters is a warning |
| `category` | `integration` | yes | string, used to group integrations |
| `icon` | `integration` | yes | path under `assets/`; the file MUST exist |
| `version` | `release` | yes | `MAJOR.MINOR.PATCH`; MUST exist in `data/releases.yaml` |
| `date` | `release` | yes | `YYYY-MM-DD` |
| `target` | `dashboard` | yes | forwarder target; `data/dashboards/<target>.yaml` MUST exist |
| `dashboard_id` | `dashboard` | yes | id of a dashboard in that file |
| `task` | `howto` | yes | the task, as a verb phrase ("Rotate the output files") |
| `since` | all | no | version the feature appeared in |
| `status` | all | no | `ga` or `prerelease` |
| `nav_title` | all | no | shorter title for navigation |
| `aliases` | all | no | list of former slugs that consumers SHOULD redirect |
| `related` | all | no | list of slugs of related documents |

Unknown keys are errors, and so are keys that belong to a different type (for
example `version` on a `howto`). Frontmatter values are plain strings; they MAY
contain placeholders (A4).

### A2.2 Section templates

Each `type` fixes its top-level (`##`) sections. Required sections are marked
`*`. Section titles MUST match the template exactly, including case. Sections
MUST appear in template order; extra top-level sections are errors.

| Type | Top-level sections, in order |
|---|---|
| `integration` | Overview\*, Prerequisites, Configuration\*, Target configuration, Data reference, Queries, Dashboards, Capacity, Troubleshooting\*, Related\* |
| `howto` | Goal\*, Prerequisites, Steps\*, Result\*, Options, Related\* |
| `format` | Overview\*, Best for\*, Usage\*, Schema\*, Examples, Notes, Related\* |
| `reference` | Overview\* first, then any number of free sections, Related\* last |
| `concept` | any number of free sections, Related\* last |
| `release` | What's new\*, Fixes, Advisories, Upgrade notes, Known issues |
| `dashboard` | Purpose\*, Panels (generated), Fields used (generated), Queries, Related\* |
| `landing` | any number of free sections |

**Generated sections.** In a `dashboard` document the sections *Panels* and
*Fields used* are generated by the compiler from
`data/dashboards/<target>.yaml` and inserted after *Purpose*. Authors MUST NOT
write them.

The body MUST start with a `##` heading: content before the first section is an
error.

## A3. Section identifiers

Every section gets an `id` derived from its title: lowercase it, delete
apostrophes (`'` and `’`), replace each run of characters that are not ASCII
letters or digits with `-`, and trim `-` from both ends. A repeated id within
one document gets `-2`, `-3` and so on. `What's new` → `whats-new`;
`The --batch-size flag` → `the-batch-size-flag`.

## A4. Placeholders and literals

These placeholders are substituted at render time from `product.yaml`. They are
stored unsubstituted in the package, so a consumer substitutes them too.

| Placeholder | Source |
|---|---|
| `{product}` | `product.name` |
| `{short}` | `product.short` |
| `{binary}` | `product.binary` |
| `{version}` | `product.version` |
| `{support_email}` | `product.support_email` |

Any other `{word}` in prose is an error. Inside code blocks and commands,
unknown braces are left alone (code legitimately contains braces).

Outside `release` documents, the body MUST NOT contain:

- the literal `product.name` (whole word, case-sensitive),
- the literal `product.binary` (whole word, case-sensitive),
- any version string matching `MAJOR.MINOR.PATCH` (for example `2.1.0`).

Link destinations and image paths are exempt. Write `{product}`, `{binary}`
and `{version}` instead.

## A5. Constructs

Each construct compiles to exactly one block type (part B lists the JSON).

| Markdown | Block | Rules |
|---|---|---|
| `##`…`#####` | `section` | No `#` in body. Max nesting depth 4. Required section names must match the template exactly. |
| paragraph | `paragraph` | Inline allowed: `**bold**`, `*italic*`, `` `code` ``, `[text](https://…)`, `[text](doc:slug)`, `[text](doc:slug#section-id)`. Nothing else. |
| `-` / `1.` lists | `list` | Nested with 4-space indent. |
| `::: steps` … `:::` containing `### Step title` + content | `steps` | Headed, numbered procedure. |
| `Term` newline `:   definition` | `definition_list` | |
| fenced code with language, optional `title="…"` | `code` | Language is required. |
| `::: command Caption` with lines `windows:`, `linux:`, `macos:` | `command` | All three keys required. A value of `none: <reason>` is allowed and keeps the tab with that note. |
| `::: note\|tip\|warning\|important Title` … `:::` | `callout` | Title required. |
| pipe table | `table` | Max 12 rows. Header row required. All rows same width. |
| `{{ flags group="x" }}`, `{{ fields dataset="x" }}`, `{{ platforms }}`, `{{ datasets }}`, `{{ releases limit=N }}` | `reference_table` | Rendered from `data/`. A hand-typed table whose header matches a reference shape (`Flag`, `Field`, `Platform` first column) is an error. |
| `::: cards` with items `- [Title](doc:slug) — one line` | `cards` | |
| `![alt](assets/path "caption")` | `image` | Alt required; file must exist. |

The details below are normative.

### A5.1 Sections

`##` opens a top-level section, `###` a subsection and so on down to `#####`
(depth 4). A heading MUST be exactly one level deeper than its parent; `##`
followed directly by `####` is an error. Headings contain plain text and code
spans only.

### A5.2 Paragraphs and inline text

Allowed inline markup is exactly: `**bold**`, `*italic*` (or `_italic_`),
`` `code` ``, and links whose destination starts with `https://` or `doc:`.
Soft and hard line breaks become a single space. Forbidden inline: raw HTML,
autolinks (`<https://…>`), images inside text, `http://` links, relative links
and bare `.html` links (use `doc:slug`).

A `doc:` link is `doc:<slug>` or `doc:<slug>#<section-id>`. The slug MUST be a
document in the project and the section id MUST exist in it.

**Flags in prose.** An inline code span whose text starts with `-` followed
by a letter (`-v`, `--batch-size`) is a flag reference. The flag name is the text up to the first `=` or space
(`` `--batch-size=500` `` names `--batch-size`). It is looked up in
`data/flags.yaml`: unknown is a warning; a flag with `status: deprecated` is an
error outside `release` documents. Matching spans compile to runs with
`flag: true`.

**Fields in prose.** An inline code span whose whole text equals a field name
in any `data/fields/*.yaml` compiles to a run with `field: true`.

### A5.3 Lists

Bullets use `-`; ordered items use `1.` (any number followed by `.`). Other
markers (`*`, `+`, `1)`) are errors. A nested list is indented by exactly 4
spaces per level, at most 3 levels deep. A list item holds one paragraph of
inline text and optionally one nested list — nothing else (use `::: steps` for
procedures that need code).

### A5.4 Containers

A container opens with a line `::: <name> <argument>` and closes with a line
that is exactly `:::`. Containers MAY nest where noted; a container that is not
closed by the end of the file is an error. Container names are `steps`,
`command`, `note`, `tip`, `warning`, `important` and `cards`.

**`steps`** — its content is a sequence of steps, each starting with a heading
(`###` by convention; any level from `###` to `#####` is accepted) that becomes
the step title. Content before the first step heading is an error. A step holds
paragraphs, lists, code, commands, callouts, tables, definition lists and
images. Steps are numbered by the renderer, so the title MUST NOT start with a
number.

**`command`** — the argument is the caption (required). Its lines are read
verbatim, not as Markdown, and MUST be exactly the three keys `windows:`,
`linux:` and `macos:`, each once, each with a non-empty value. The value
`none: <reason>` means the command does not apply on that OS; the renderer
still shows the tab, with the reason.

```markdown
::: command Start the agent
windows: {binary}.exe run --config C:\ProgramData\{binary}\agent.yaml
linux: sudo {binary} run --config /etc/{binary}/agent.yaml
macos: {binary} run --config /usr/local/etc/{binary}/agent.yaml
:::
```

**Callouts** (`note`, `tip`, `warning`, `important`) — the argument is the
title (required). The body holds paragraphs, lists, code, commands, tables,
definition lists and images. Callouts do not nest and do not hold steps.

**`cards`** — the body is one `-` list. Each item is exactly a `doc:` link,
then ` — ` (space, em dash, space), then one line of plain text.

### A5.5 Code

A fenced block (```` ``` ```` or `~~~`) MUST have a language (`[a-z0-9_+-]+`)
and MAY have `title="…"`. No other info-string attributes are allowed.
Indented code blocks are errors.

### A5.6 Definition lists

A term on its own line, followed by one or more lines starting with `:` and
spaces. Each definition is one paragraph of inline text.

### A5.7 Tables

GitHub pipe tables. The header row is required and every header cell is
non-empty. At most 12 body rows. Every row MUST have the same number of cells
as the header. A table whose first header cell is `Flag`, `Field` or
`Platform` (any case) is a hand-typed reference table and is an error: use the
matching `{{ … }}` reference instead.

### A5.8 Reference tables

A paragraph consisting of exactly one `{{ … }}` expression is a reference
table. `{{` anywhere else is an error.

| Expression | Arguments | Rows |
|---|---|---|
| `{{ flags }}` | `group="<id>"` optional | flags, in file order |
| `{{ fields dataset="<id>" }}` | `dataset` required | fields of that dataset |
| `{{ platforms }}` | none | platforms |
| `{{ datasets }}` | none | datasets |
| `{{ releases }}` | `limit=N` optional | releases, newest first |

The filter MUST select at least one row. The compiler resolves the rows into
the block, so the package is self-contained (B3.10).

### A5.9 Images

A paragraph consisting of exactly one image is an `image` block. The alt text
is required, the path MUST start with `assets/` and the file MUST exist. The
optional title becomes the caption.

### A5.10 Forbidden everywhere

Raw HTML, inline styles, emoji, typed bullet glyphs (`•`), `#` headings,
`######` headings, blockquotes, thematic breaks (`---` in the body), indented
code, bare `.html` links, hand-written flag, field or platform tables, and
anything not listed in this section. The text `_fill:` (the skeleton marker)
MUST NOT remain anywhere in a document.

## A6. Data files

Each data file has a JSON Schema in `schemas/1.0/data/`. Every file is a YAML list
at the top level.

**`data/flags.yaml`** — one entry per flag:
`name` (starts with `-`), `group` (id, lowercase), `type` (`string`, `int`,
`bool`, `duration`, `path`, `list`), `default` (scalar or null), `env`
(environment variable or empty), `description`, `platforms[]` (values are `os`
ids from `platforms.yaml`), `status` (`ga`, `prerelease`, `deprecated`),
`replaced_by` (flag name, required when deprecated), `since` (version).

**`data/fields/<dataset>.yaml`** — one entry per field:
`name`, `type` (`string`, `int`, `float`, `bool`, `timestamp`, `object`,
`list`), `required` (bool), `description`, `example` (scalar), `levels[]`
(output verbosity levels that emit the field: `minimal`, `standard`,
`verbose`). The file name MUST be a dataset id.

**`data/platforms.yaml`** — `os` (id: lowercase), `version` (supported OS
versions, as text), `arch[]` (`amd64`, `arm64`), `capabilities{}` (map of
capability name to bool).

**`data/datasets.yaml`** — `id`, `description`, `avg_size_kb` (average record
size), `typical_count` (typical records per agent per day).

**`data/dashboards/<target>.yaml`** — one entry per dashboard: `id`, `title`,
`purpose`, `panels[]` of `{title, query, fields[]}` (every field MUST exist in
some dataset), `screenshot` (optional path under `assets/`).

**`data/releases.yaml`** — newest first: `version`, `date` (`YYYY-MM-DD`),
`kind` (`major`, `minor`, `patch`), `items[]` of `{id, type, text}` where
`type` is `feature`, `fix`, `change` or `deprecation`, `advisories[]` of
`{id, text}`, `upgrade_notes[]` (strings).

Ids (flag names, field names within a dataset, dataset ids, platform `os`,
dashboard ids within a target, release versions) MUST be unique.

## A7. product.yaml

```yaml
name: Lanternfish            # product name, as written in prose
short: lf                    # short name; names the package file
binary: lanternfish          # executable name
version: 1.4.0               # version being documented
support_email: support@example.com
nav:
  - group: Get started
    items:
      - index
      - doc: install
        children: [first-pipeline]
  - group: Dashboards
    items:
      - group: Warehouse A
        from: dashboards/warehouse-a
  - group: Releases
    from: releases
    limit: 3
```

### A7.1 Navigation

`nav` is an ordered list of groups. A group is `{group: "Title", items: [...]}`
or a generated group `{group: "Title", from: <source>, limit: N}`. An item is
one of:

- a slug (string);
- `{doc: slug, children: [...]}` — a document with child items;
- a group, as above (a nested group).

`from` is `dashboards/<target>` (every `dashboard` document with that
`target`, in data-file order) or `releases` (every `release` document, newest
first). `limit` is optional and caps the generated list.

Every slug MUST exist. Every document MUST be reachable — listed in `nav`,
produced by a generated group, or named in some document's `related` list.
Navigation is at most 3 levels deep, counting the top-level group as level 1.

# Part B — The package

## B1. Container

`docpack check` writes `dist/<short>-<version>.zip`. Entries are written in
sorted order with a fixed timestamp, so the same input always produces the
same bytes.

```text
manifest.json
product.json
documents/<slug>.json
data/flags.json
data/platforms.json
data/datasets.json
data/releases.json
data/fields/<dataset>.json
data/dashboards/<target>.json
assets/...
```

`data/*.json` are the YAML files converted to JSON, unchanged in shape (a
missing YAML file produces no JSON file). `assets/` is a copy of the project's
`assets/` directory.

## B2. manifest.json

Validates against `schemas/1.0/manifest.schema.json`.

```json
{
  "schema_version": "1.0",
  "product": "lf",
  "version": "1.4.0",
  "generator": "docpack 0.1.0",
  "nav": [
    {"title": "Get started", "children": [
      {"title": "Lanternfish", "doc": "index"},
      {"title": "Install the agent", "doc": "install", "children": [
        {"title": "Ship your first file", "doc": "first-pipeline"}
      ]}
    ]}
  ],
  "documents": [
    {"slug": "index", "type": "landing", "title": "{product}", "hash": "sha256:9f2c…"}
  ],
  "assets": ["assets/icons/warehouse-a.svg"]
}
```

`nav` is fully resolved: generated groups are expanded and each node carries
the title to show (`nav_title` if set, else `title`). A node has `doc`, or
`children`, or both. `hash` is the SHA-256 of the exact bytes of
`documents/<slug>.json`.

## B3. Documents

`documents/<slug>.json` validates against `schemas/1.0/document.schema.json`. Its
header fields are the frontmatter keys (A2.1), with the same names; `body` is
the ordered list of top-level blocks — always `section` blocks.

```json
{
  "type": "howto",
  "slug": "rotate-output",
  "title": "Rotate output files",
  "summary": "Keep local output files from filling the disk.",
  "task": "Rotate the output files",
  "related": ["file-output"],
  "body": [ { "type": "section", "id": "goal", "title": "Goal", "level": 2, "body": [] } ]
}
```

### B3.0 Text runs

Inline text is an array of runs, each validated by
`schemas/1.0/text-run.schema.json`. A run is `{t, bold?, italic?, code?, link?,
flag?, field?}`; absent booleans are false. Adjacent runs with identical
attributes are merged. `link` is the destination as written (`https://…` or
`doc:slug#id`). Placeholders stay unsubstituted.

```json
[{"t": "Set "}, {"t": "--batch-size", "code": true, "flag": true}, {"t": " to "}, {"t": "500", "bold": true}]
```

The twelve block types follow, one example each. Every block has `type`.

### B3.1 section

`level` is the heading level (2–5). `body` holds any blocks, including nested
sections.

```json
{"type": "section", "id": "configuration", "title": "Configuration", "level": 2,
 "body": [{"type": "paragraph", "text": [{"t": "Edit the file."}]}]}
```

### B3.2 paragraph

```json
{"type": "paragraph", "text": [{"t": "See "}, {"t": "Install", "link": "doc:install"}, {"t": "."}]}
```

### B3.3 list

Items carry `text` and optionally nested `items`.

```json
{"type": "list", "ordered": false, "items": [
  {"text": [{"t": "Linux"}], "items": [{"text": [{"t": "systemd unit"}]}]},
  {"text": [{"t": "Windows"}]}
]}
```

### B3.4 steps

```json
{"type": "steps", "steps": [
  {"title": "Create the configuration", "body": [{"type": "paragraph", "text": [{"t": "Open an editor."}]}]},
  {"title": "Start the agent", "body": []}
]}
```

### B3.5 definition_list

```json
{"type": "definition_list", "items": [
  {"term": [{"t": "Batch"}], "definition": [{"t": "A group of records sent together."}]}
]}
```

### B3.6 code

```json
{"type": "code", "language": "yaml", "title": "agent.yaml", "code": "inputs:\n  - path: /var/log/app.log"}
```

### B3.7 command

Each variant is `{"command": "…"}` or `{"none": "<reason>"}`.

```json
{"type": "command", "caption": "Check the version", "variants": {
  "windows": {"command": "{binary}.exe version"},
  "linux": {"command": "{binary} version"},
  "macos": {"none": "Not supported on macOS."}
}}
```

### B3.8 callout

`kind` is `note`, `tip`, `warning` or `important`.

```json
{"type": "callout", "kind": "warning", "title": "Restart required",
 "body": [{"type": "paragraph", "text": [{"t": "Restart the agent after editing."}]}]}
```

### B3.9 table

`header` is a list of cells; `rows` a list of rows of cells; a cell is a run
array.

```json
{"type": "table", "header": [[{"t": "Mode"}], [{"t": "Meaning"}]],
 "rows": [[[{"t": "tail"}], [{"t": "Read new lines only."}]]]}
```

### B3.10 reference_table

`source` is `flags`, `fields`, `platforms`, `datasets`, `releases`, or — only
in generated dashboard sections — `panels` and `dashboard_fields`. `filter`
and `limit` repeat the expression's arguments. `columns` and `rows` are the
resolved table; cells are plain strings, and flag and field names appear as
written in the data.

```json
{"type": "reference_table", "source": "flags", "filter": {"group": "output"},
 "columns": ["Flag", "Type", "Default", "Env", "Description", "Platforms", "Status"],
 "rows": [["--output-dir", "path", "./out", "LF_OUTPUT_DIR", "Directory for output files.", "linux, macos, windows", "ga"]]}
```

Columns by source:

| Source | Columns |
|---|---|
| `flags` | Flag, Type, Default, Env, Description, Platforms, Status |
| `fields` | Field, Type, Required, Description, Example |
| `platforms` | Platform, Version, Arch, Capabilities |
| `datasets` | Dataset, Description, Avg size (KB), Typical count |
| `releases` | Version, Date, Kind, Changes |
| `panels` | Panel, Query, Fields |
| `dashboard_fields` | Field, Dataset, Type, Description |

### B3.11 cards

```json
{"type": "cards", "items": [
  {"title": "Warehouse A", "doc": "warehouse-a", "text": "Forward records to Warehouse A."}
]}
```

An item MAY carry `section` when the link names one.

### B3.12 image

```json
{"type": "image", "src": "assets/dashboards/a-overview.svg", "alt": "Overview dashboard", "caption": "The overview dashboard."}
```

## B4. product.json and data

`product.json` holds `name`, `short`, `binary`, `version` and `support_email`
and validates against `schemas/1.0/product.schema.json` (navigation is in the
manifest, resolved). Each `data/*.json` validates against the matching schema
in `schemas/1.0/data/`.

## B5. Versioning

`schema_version` is `MAJOR.MINOR`, starting at `1.0`. Adding an optional field
or a new block type bumps MINOR; consumers MUST ignore fields they do not know
and SHOULD render unknown block types as nothing. Removing or changing the
meaning of anything bumps MAJOR. The schemas of each version live in
`schemas/<version>/`, and every `$id` is the raw URL of its file on the `main`
branch, for example
`https://raw.githubusercontent.com/42kohd/docpack/main/schemas/1.0/block.schema.json`.
A new version gets a new directory; published directories do not change.

# Part C — The checker

## C1. Output

`docpack check [dir]` prints one diagnostic per line:

```text
docs/<file>.md:<line>  <rule-id>  <message>. <fix>
```

The fix is a concrete instruction an author can act on or paste into a
language model. Warnings use the same shape with the message prefixed by
`warning: `. `--format json` prints an array of
`{file, line, rule, message, fix, severity}`. Diagnostics are sorted by file,
then line, then rule. Line 0 means "the whole file".

On zero errors the checker writes the package and prints one summary line,
exiting 0. Any error writes nothing and exits 1. `--warnings-as-errors`
counts warnings as errors.

## C2. Rule ids

Rule ids are stable; new rules get new ids and ids are never reused.

| Rule | Severity | Meaning |
|---|---|---|
| `alias-duplicate` | error | An alias equals a slug or another alias. |
| `asset-unused` | error | A file in `assets/` is not referenced by any document or data file. |
| `block-forbidden` | error | Blockquote, thematic break, indented code, or a heading inside a container. |
| `bullet-glyph` | error | A typed bullet character such as `•`. |
| `cards-item` | error | A cards item is not `[Title](doc:slug) — text`. |
| `cmd-caption` | error | `::: command` without a caption. |
| `cmd-duplicate-key` | error | A command key appears twice. |
| `cmd-empty` | error | A command key has no value. |
| `cmd-missing-variant` | error | A command lacks `windows:`, `linux:` or `macos:`. |
| `cmd-unknown-key` | error | A command line is not one of the three keys. |
| `code-info` | error | A code fence has attributes other than `title="…"`. |
| `code-language` | error | A code fence has no language. |
| `container-nesting` | error | A container where it may not appear (steps in a callout, a callout in a callout, …). |
| `container-stray` | error | A `:::` line with no open container. |
| `container-unclosed` | error | A container is not closed. |
| `container-unknown` | error | A container name that is not in the dialect. |
| `content-before-section` | error | Body content before the first `##`. |
| `dashboard-missing` | error | `dashboard_id` is not in `data/dashboards/<target>.yaml`. |
| `data-duplicate` | error | A duplicate id in a data file. |
| `data-missing` | error | `product.yaml` is missing, or `docs/` is empty. |
| `data-ref` | error | A data file references something that does not exist. |
| `data-schema` | error | A data file or `product.yaml` does not match its schema. |
| `deflist-content` | error | A definition is not one paragraph. |
| `doc-nested` | error | A `.md` file in a subdirectory of `docs/`. |
| `emoji` | error | An emoji character. |
| `fill-left` | error | A `_fill:` skeleton marker remains. |
| `flag-deprecated` | error | A deprecated flag is used outside a release note. |
| `flag-unknown` | warning | A code span starting with `-` is not in `data/flags.yaml`. |
